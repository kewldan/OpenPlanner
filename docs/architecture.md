# Архитектура OpenPlanner

Принятые решения и их обоснование: [`decisions.md`](decisions.md). Здесь — как всё складывается вместе.

## Процессы и потоки

```
┌───────────────────────────── Вебвью (WKWebView / WebView2 / WebKitGTK) ─────────────────────────────┐
│                                                                                                     │
│  UI-поток: React + TypeScript                     Web Worker: op-engine (WASM)                      │
│  ┌──────────────────────────────┐   команды  →   ┌─────────────────────────────────────────┐        │
│  │ панели, инспекторы, таблицы, │                │ op-model: документ, команды, undo,      │        │
│  │ диалоги, ⌘K, горячие клавиши │   ← диффы,     │           варианты, производные данные  │        │
│  │ ввод мыши/клавиатуры → канвас│     выборки    │ op-render: wgpu (WebGPU | WebGL2)       │        │
│  └──────────────────────────────┘                │   → OffscreenCanvas                     │        │
│                                                  │ op-export: листы → PDF/SVG/DXF/XLSX     │        │
│                                                  └─────────────────────────────────────────┘        │
└────────────────────────────────────────────┬────────────────────────────────────────────────────────┘
                                             │ Tauri IPC (файлы, тяжёлые задачи, прогресс)
┌────────────────────────────────────────────┴────────────────────────────────────────────────────────┐
│  Tauri 2 (нативный Rust): ФС (.oplan, журналы, файлы экспорта), диалоги; позже — тяжёлые задачи     │
└─────────────────────────────────────────────────────────────────────────────────────────────────────┘
```

- **UI-поток** не держит модель. Он хранит только проекции, нужные панелям (выделение, свойства, списки), и обновляет их по диффам.
- **Воркер** владеет документом и рендерером. Ввод на холсте (указатель, клавиши) пересылается в воркер. Инструменты (стена, проём, размер) живут в ядре, чтобы превью и привязки считались рядом с геометрией.
- **Нативная часть** выполняет то, что требует диска, всех ядер CPU или долгой работы. Задачи отменяемые и сообщают прогресс.
- В **веб-версии** нативные сервисы заменяются WASM-сборкой тех же crates, а файлы открываются выбором файла и сохраняются скачиванием (позже — File System Access API).
- Разница между десктопом и браузером спрятана за интерфейсом `Platform` (`packages/editor/src/platform`): файлы, диалоги, журнал, заголовок окна.

## Модель

- Единицы — миллиметры, `f64`. Углы — радианы внутри, градусы в UI. Ось Y направлена вниз (как на экране и листе).
- Документ: обмер (общий для всех вариантов) + варианты. Элемент без поля `variant` — обмер; с `variant` — новый элемент этого варианта. Вариант хранит название и список демонтированных элементов обмера. Вид варианта — проекция `op_model::view::project`: обмер без демонтажа плюс элементы варианта; статус «существующий / демонтаж / новый» вычисляется из этого. Позже в варианты попадут мебель, инженерия и отделка.
- Элементы стадии 1 (`crates/op-model/src/document.rs`):
  - слои (системные и пользовательские; видимость, блокировка);
  - узлы и стены (толщина, линия привязки: по оси / слева / справа, высота);
  - проёмы в стенах (дверь, окно, арка; положение от узла `a`, ширина, высота, низ от пола, петли и сторона открывания);
  - помещения (точка подписи, название, высота потолка; контур и площадь вычисляются);
  - размеры (концы — узлы или точки, смещение размерной линии), выноски, подложки (изображение в `assets/`, положение, масштаб, прозрачность).
- Стадия 3: варианты (`Variant`: название, список демонтажа), поле `variant` у элементов, материал стены (`Wall.material`: газобетон, ГКЛ, кирпич).
- Стадия 4: графы основной надписи в `meta`, настройки чертежей (`drawing`). Стадия 5: привязка к местности (`site`: север на плане, широта, долгота, часовой пояс) и сохранённые ракурсы 3D (`views`). Стадия 6: мебель (`Furniture`: позиция каталога или своя модель GLB в `assets/furniture/`, центр, поворот, отражение, ширина, глубина, высота, высота над полом) на системном слое «Мебель». Стадия 7: точки электрики (`Device`: тип, центр, поворот, высота, мощность, световой поток, группа, клавиши выключателя → светильники) на слое «Электрика», группы щита (`circuits`) и сценарии освещения (`scenes`). Стадия 8: сантехнические точки (`PlumbingPoint`: вывод, стояк или коллектор системы ХВС, ГВС или канализации; центр, поворот, отметка, диаметр, назначение, прибор) и трубы (`Pipe`: система, диаметр, вершины с отметками, признак автоматической прокладки) на слое «Сантехника». Стадия 11: этажи (`levels`: название, отметка; поле `level` у узлов, помещений, размеров, выносок, подложек, мебели, точек и труб — стена и проём на этаже своих узлов), зоны тёплого пола (`heating`), готовые кадры рендера (`renders`, файлы — `assets/renders/`). Формат 11. Стадия 10: прайс проекта (`prices`: код, раздел, наименование, работа или материал, единица, цена, правило объёма `Measure`, норма, запас, история цен) и ручные объёмы строк сметы (`overrides`: позиция, помещение, количество). Стадия 9: материалы проекта (`materials`) и отделка поверхностей помещений (`finishes`: помещение, пол / потолок / стены или одна стена по букве развёртки, материал, полоса высот, раскладка — рисунок, шов, сдвиг рядов, старт).
- Все изменения — команды (`put`, `remove`, `putAsset`, `removeAsset`, `batch` и команды свойств проекта). Команда атомарна, обратима и сериализуема (для журнала автосохранения).
- Производные данные (`crates/op-engine/src/derived.rs`): контуры стен со стыками, объединение стен минус проёмы, области помещений с площадью и периметром, длины. На стадии 1 пересчитываются целиком при каждом изменении (миллисекунды на квартиру); позже — инкрементально по зависимостям.
- Идентификаторы стабильные (монотонные ULID, выдаёт движок). Ссылки между элементами — по ID.

## Протокол UI ↔ воркер

- Сообщения — JS-объекты (serde-wasm-bindgen). Типы TS генерируются из Rust через tsify (`crates/op-engine/src/protocol.rs`).
- UI → воркер: сообщения `ToEngine` без ответа (команды, отмена, вид, выбор инструмента, ввод указателя, Esc/Enter, числовой ввод, выделение, удаление) и вызовы с ответом (`exportFile`, `importFile`, `addUnderlay`, `importScan`, `replayJournal`, `journalHeader`, `documentTitle`, `drawingSet`, `exportDrawings`, `zipFiles`, `importFurniture`, `exportEstimate`, `exportPrices`, `importPrices`). Всё выполняется строго в порядке отправки.
- Распознавание скана — второй воркер с тем же WASM-модулем (`packages/engine-client/src/scan.worker.ts`, функция `analyzeScan`): прогресс по этапам, отмена остановкой воркера. Результат (`ScanResult`) мастер показывает пользователю и вместе с ответами и параметрами передаёт движку вызовом `importScan`.
- Воркер → UI: события `FromEngine` — документ (целиком, без двоичных файлов), вычисленные величины (площади, длины), состояние истории (`canUndo`, `canRedo`, `dirty`), вид, выделение, инструмент и его шаг, курсор после привязки (с длиной и углом рисуемого отрезка), запрос ввода текста, строки журнала, ошибки.
- Вид холста (`setView`): обмер, вариант или сравнение двух видов рядом (только просмотр). Движок держит проекцию текущего вида и адаптирует к нему каждую правку (`crates/op-engine/src/variants.rs`): в варианте новые элементы помечаются вариантом, удаление элемента обмера становится демонтажом; в обмере удаление уносит зависящие элементы вариантов. Варианты создаются, копируются и удаляются сообщениями `createVariant` / `deleteVariant`, демонтаж — `setDemolished` или инструментом «Демонтаж». После правки движок присылает `variantsSummary` — площади и изменения по каждому виду.
- 3D-вид: `set3d` (включение, орбита или прогулка, потолки, белая модель, срез, солнце — состояние окна, не документа), `camera3d` (поворот, сдвиг, приближение, перемещение), `resetCamera3d`, `saveView3d` / `applyView3d`. Движок отвечает `view3dChanged` (настройки, камера, положение солнца). Ракурсы и привязка к местности — свойства проекта (`setViews`, `setSite`), отменяются как любая правка. В 3D инструменты плана выключены; мышь, колесо и WASD UI переводит в `camera3d`.
- Ввод на холсте — левая кнопка указателя в CSS-пикселях холста с модификаторами (Shift — 0/45/90° и добавление к выделению, Alt — без привязок). Средняя кнопка, пробел и прокрутка панорамируют, ⌘/Ctrl + прокрутка масштабирует — это UI переводит в `pan`/`zoom`.
- Большие данные (файл проекта, скан, превью) передаются как `Transferable` (ArrayBuffer), без копирования.

## Скан (`crates/op-scan`)

```
файл (GLB / OBJ / PLY / ZIP / RoomPlan JSON)
  → выборка поверхности: точки плана (мм, Z вверх) с нормалями и площадью
  → пол и потолок → ориентации стен → грани и сетки заполненности
  → стены (пары граней / одиночные) + проёмы → стыки
  → вопросы проверки с уверенностью, вид сверху (PNG)
ответы + параметры → план (узлы, стены, проёмы) → команды движка
```

- Данные RoomPlan, если есть, заменяют распознавание стен и проёмов.
- `op_scan::apply` превращает результат, ответы и параметры в план; движок (`crates/op-engine/src/scan_import.rs`) добавляет помещения по замкнутым контурам и выполняет всё одной правкой.
- Синтетические сканы для тестов — `op_scan::synth`.

## Рендерер

- wgpu, бэкенд WebGPU, при отсутствии — WebGL2. Все эффекты, зависящие от compute, имеют путь без compute.
- Сцена (`op_render::scene::Scene`) строится в движке на CPU и не зависит от GPU: заливки (тесселяция lyon), линии и маркеры постоянной экранной толщины (экземпляры, сглаживание и штрихи в шейдере), глифы, изображения. Два слоя: документ (пересобирается при изменении документа) и оверлей (выделение, ручки, превью инструмента, привязки — при движении указателя).
- Текст — SDF-атлас встроенного шрифта Onest (`op_render::text`): размер в мм плана или в пикселях экрана, светлая обводка отдельным проходом.
- Штриховки — позже (стадия 4, чертежи).
- Облако точек: инстансинг точек, уровни детализации.
- 3D (`op_render::three`, `gpu3d.rs`, `three.wgsl`): сетки с нормалью и цветом, буфер глубины, отсечение задних граней, стёкла с прозрачностью. Свет — небо (полусфера) и солнце с картой теней (2048², сравнительный сэмплер, 4 выборки); compute не нужен, работает и в WebGL2. Сетку строит движок (`crates/op-engine/src/model3d.rs`) из текущего вида: стены с вырезами проёмов, перемычки и подоконные части, открытые полотна дверей, стёкла, полы и потолки помещений; срез по высоте обрезает геометрию на CPU. Камера — орбита или прогулка на высоте глаз (`camera3d.rs`), солнце — по дате, времени и привязке к местности (`sun.rs`). Мебель из GLB — стадия 6.
- Холст плана всегда светлый, независимо от темы UI.

## Формат `.oplan`

```
project.oplan (ZIP)
├─ manifest.json        версия формата, приложение, даты
├─ model.json           обмер, варианты, слои, настройки проекта
├─ scan/                исходные файлы сканов
├─ assets/              изображения подложек; позже — GLB, текстуры
├─ previews/            миниатюры для стартового экрана
└─ renders/             сохранённые кадры
```

- Прайс проекта (`prices`) и ручные объёмы сметы (`overrides`) хранятся в `model.json`, как и остальной документ: смета воспроизводима из файла и отменяется по шагам.
- Схема `model.json` — JSON Schema в `schema/model.schema.json` под MIT. Генерируется из Rust-типов (schemars); тест в `op-model` следит, чтобы файл не отставал.
- Миграции между версиями формата — цепочка функций в `op-format` (`N → N+1`). Компиляция падает, если версия формата увеличена без миграции.
- Запись атомарная: во временный файл рядом и переименование.

## Файлы и автосохранение

- Проект с файлом автосохраняется каждые 30 секунд, если есть изменения.
- Каждое изменение истории (выполнить, отменить, повторить) движок выдаёт строкой журнала. UI дописывает строки в журнал проекта: `<project>.oplan.journal` рядом с файлом или `recovery/untitled.oplan.journal` в папке данных приложения для проекта без файла (в браузере — localStorage).
- После сохранения журнал начинается заново. Строки, пришедшие до выгрузки файла, уже в файле; пришедшие после — уходят в новый журнал.
- При открытии проекта (или запуске приложения для несохранённого проекта) непустой журнал предлагается восстановить: операции воспроизводятся поверх файла, вместе с историей отмены.
- Состояние «есть изменения» считается в ядре по идентификаторам состояний истории: отмена до сохранённого состояния снимает признак, новая ветка — нет.
- Нативные команды принимают только пути `.oplan` и `.oplan.journal`; запись экспорта (`write_export`) — только `pdf`, `svg`, `dxf`, `png`, `xlsx`, `zip`.

## Мебель

- Каталог (`crates/op-engine/src/furniture.rs`) — позиции с размерами по умолчанию; условные обозначения и 3D-формы строятся процедурно по размерам предмета, в локальных осях (ширина вдоль X, спинка на −Y). UI получает каталог событием `catalog` с иконками-путями SVG.
- Инструмент «Мебель» (`furnitureTool`): превью у курсора, щелчок ставит предмет; если спинка ближе 24 px к грани стены, предмет встаёт к ней вплотную лицом в помещение. То же при перетаскивании выделенного предмета; Alt отключает привязку. `transformFurniture` поворачивает и отражает выделенное (или предмет инструмента).
- Перетаскивание из каталога: UI переводит события drag-and-drop в `pointer` инструмента «Мебель».
- Свои модели: вызов `importFurniture` читает GLB (читатель `op-scan`), сохраняет файл в проекте, размеры предмета — габарит модели; на плане — контур выпуклой оболочки вида сверху, в 3D — треугольники модели, растянутые на размеры предмета.
- Мебель — элементы вида, как стены: новые в варианте помечаются вариантом, мебель обмера в варианте можно убрать (список демонтажа).

## Электрика и освещение

- Каталог точек, условные обозначения, привязка к грани стены, распределение по группам, трассы и отчёт — `crates/op-engine/src/electric.rs`; расчёты (ток, падение напряжения, кабель и автомат, состав щита, освещённость и нормы) — чистые функции `crates/op-calc`.
- Инструмент «Электроточка» (`deviceTool`): превью у курсора, щелчок ставит точку; настенная точка ближе 40 px к грани встаёт к ней лицом в помещение (Alt — без привязки). Каталог приходит событием `deviceCatalog`.
- `autoCircuits` одной командой задаёт группы и проставляет группу точкам. После каждого изменения движок присылает событие `electrical`: группы с нагрузкой, током, длиной кабеля, ΔU и предупреждениями, состав щита, освещённость помещений, точки без группы.
- Удаление светильника убирает его из клавиш выключателей и сценариев; копирование в вариант переназначает клавиши на копии светильников.
- Точки в 3D — накладки на стене, светящиеся плафоны на потолке.

## Сантехника

- Каталог точек, обозначения, выводы под приборы, прокладка, проверки и спецификация — `crates/op-engine/src/plumbing.rs`; уклоны, проверки канализации, хлысты и фитинги на поворотах — чистые функции `crates/op-calc` (`plumbing.rs`).
- Инструмент «Сантехника» (`plumbingTool`): вывод встаёт на грань стены (центр — на самой грани), стояк и коллектор — где щёлкнули. Инструмент «Труба» (`pipeTool`): вершины щелчками с привязкой к центрам точек, Shift — по осям, двойной щелчок или Enter — конец; отметки вершин считает движок (вода — на отметке начала, канализация — с нормальным уклоном вниз).
- `fixtureOutlets` ставит выводы под приборы каталога мебели (ванна, душ, раковины, унитаз, стиральная машина), у которых выводов ещё нет: системы, отметки и диаметры — из таблицы прибора, вывод ссылается на прибор. `routePipes` удаляет автоматические трубы вида и прокладывает заново: от каждого вывода без ручной трубы — к коллектору своей системы (вода) или к ближайшему стояку, двумя участками по осям с меньшим числом пересечений стен.
- После каждой правки движок присылает `plumbing`: трубы с длиной, уклоном и замечаниями, трубы и фитинги, выводы без трубы, общие замечания (нет стояка, ревизия стояка закрыта мебелью).
- В 3D трубы — бруски сечением в диаметр цветом системы, стояки — до потолка.

## Отделка

- Библиотека материалов, поверхности, раскладка, расход и подбор старта — `crates/op-engine/src/finish.rs`; грани помещения (буквы стен) — общий модуль `surfaces.rs` для отделки и развёрток; раскладка штучного материала (обрезка ячеек по поверхности, узкие подрезки, перебор старта) — `op_geom::tiling`; нормы расхода — `op_calc::finish`.
- Отделка — список документа, правится целиком командой `setFinishes`; материалы проекта — `setMaterials`. Встроенная библиотека приходит событием `materialLibrary`, расчёт — событием `finishes` (поверхности помещений с площадями, по отделке — площадь, целые и подрезанные элементы, узкие подрезки, расход с упаковками, замечания; итоги по материалам).
- `optimizeLayout` подбирает старт раскладки с наименьшим числом узких подрезок и записывает его в отделку. `showFinishes` включает раскладку пола на плане (режим «Отделка»).
- Пол и потолок в 3D — цветом материала отделки.

## Этажи

- Этаж — проекция, как вариант: `op_model::view::project_level(doc, variant, level)` оставляет элементы этажа (стены и проёмы — по узлам). Движок держит текущий этаж (`setLevel`, `addLevel`, `deleteLevel` — со всем, что на этаже, одним действием) и помечает им новые элементы при адаптации команд.
- План, инструменты, электрика, сантехника, отделка, климат — по текущему этажу; сводка вариантов, смета и IFC — по всем этажам (помещения с названием этажа); чертежи — по этажу из запроса; в 3D под текущим этажом показаны нижние на своих отметках.

## Климат

- Точки климата — виды `Device` (терморегулятор, внутренний и наружный блоки кондиционера, бризер, решётка, вытяжной вентилятор) в каталоге электрики, режим «Климат». Зоны тёплого пола — список `heating` (`setHeating`): помещение, удельная мощность, отступ, терморегулятор.
- `crates/op-engine/src/climate.rs` (нормы — `op_calc::climate`): площадь обогрева (пол минус отступ по периметру и мебель на полу), мощность, воздухообмен по установленным устройствам против нормы помещения, рекомендуемая мощность охлаждения. Мощность терморегулятора в расчёте групп — сумма его зон; тёплый пол и кондиционер получают свои группы.

## Импорт, IFC, рендер, веб

- DXF: `op_export::dxf::read` (текстовый DXF: отрезки, полилинии, дуги, окружности; единицы `$INSUNITS`, кодировка UTF-8 или cp1251) → `crates/op-engine/src/dxf_import.rs`: подложкой (растр в масштабе чертежа) или стенами по линиям выбранных слоёв одним действием. glTF: `.gltf` с буферами data URI читается тем же кодом, что GLB (`op_scan::io`).
- IFC 4: `op_export::ifc` пишет STEP-файл из простой модели (стены — выдавленные контуры, проёмы — вырезы с дверями и окнами, помещения с площадью, мебель — бруски, этаж на этаж); модель собирает `crates/op-engine/src/ifc.rs`. Формат экспорта `ifc` в окне «Чертежи».
- Рендер: `op_render::trace` — трассировка путей на CPU (BVH, солнце с мягкой тенью, небо, три отскока, автоэкспозиция и ACES). Движок отдаёт сцену и камеру блоком байт (`renderInput`), воркер `render.worker.ts` трассирует (`traceImage`), кадр сохраняется в проекте (`addRender`, `assets/renders/`). Очередь — в UI (`packages/editor/src/render/queue.ts`).
- Веб-версия: тот же фронтенд с платформой браузера (`bun run build:web`, относительные пути). Гостевая ссылка — `.oplan` без файлов (`exportGuest`) в base64url в якоре адреса (`#guest=`); веб-версия открывает её только для просмотра (`setReadOnly`), без журнала и сохранения. Облачная папка: десктоп сверяет отметку файла (`file_stamp`) при фокусе окна и перед автосохранением; изменённый на другом устройстве файл открывается заново, несохранённые правки — копией «(конфликт …)» рядом.

## MCP

- Агент подключается к открытому приложению: MCP-клиент запускает `openplanner-desktop mcp` (мост stdio, `apps/desktop/src-tauri/src/mcp.rs`), мост соединяется с приложением по TCP на 127.0.0.1 с токеном из `mcp.json` в папке данных (или запускает приложение). Приложение отдаёт строки окну событием `mcp-request`, ответ — командой `mcp_reply`.
- Окно (`packages/editor/src/mcp/relay.ts`) выполняет `save_project` и `open_project` через контроллер проекта, остальное передаёт движку вызовом `mcpMessage`; движок (`crates/op-engine/src/mcp.rs`) отвечает строкой JSON-RPC, присылает события (UI обновляется как от своих правок) и файлы экспорта, которые окно пишет по пути агента (`Platform.writeExport`).

## Смета

- Объёмы, строки, итоги, закупки, типовой прайс, импорт и экспорт — `crates/op-engine/src/estimate.rs`; количество по норме и запасу и стоимость — `op_calc::estimate`; CSV и чтение первого листа XLSX — `op_export::csv`, `op_export::xlsx::read`.
- Прайс правится целиком командой `setPrices`, ручные объёмы — `setOverrides`. `defaultPrices` добавляет позиции типового прайса, которых нет по коду. После каждой правки движок присылает `estimate`: строки (позиция × помещение или общая строка), итоги по разделам и помещениям, работы, материалы, закупки. Сводка вида (`variantsSummary`) несёт стоимость каждого варианта.
- Объёмы, которые относятся к помещению (площади, точки, мебель, отделка), считаются по помещениям; демонтаж, перегородки, проёмы, кабель и трубы — общей строкой.
- Вызовы `exportEstimate` и `exportPrices` отдают XLSX или CSV (разделитель «;», UTF-8 с BOM); `importPrices` читает CSV или XLSX и сливает с прайсом проекта одной командой. Файл прайса выбирается через `Platform.openTable` (в десктопе — нативная команда `read_table`, только `.csv` и `.xlsx`), сохраняется через `Platform.saveExport`.

## Чертежи и экспорт

- Комплект листов собирает движок (`crates/op-engine/src/sheets.rs`) из документа целиком: обмерный план и для варианта — демонтаж, монтаж перегородок, помещения; затем план расстановки мебели со спецификацией, планы розеток, освещения, выключателей и электропроводки с ведомостями, группами и составом щита, планы водоснабжения и канализации с ведомостями выводов и спецификацией (`sheets/plumbing.rs`), планы полов с раскладкой и потолков с ведомостью отделки и расходом (`sheets/finishes.rs`) и развёртки стен итогового вида с мебелью у стен, отделкой, раскладкой и узкими подрезками (`sheets/elevations.rs`). Лист — `op_export::Sheet`: примитивы в мм бумаги, видовой экран с планом в масштабе, рамка и основная надпись, таблицы и легенды.
- Вызов `drawingSet` отдаёт окну «Чертежи» листы в SVG (текст контурами), масштаб и предупреждения; `exportDrawings` — файл PDF, SVG, DXF, XLSX или «Пакет для бригады» (ZIP). PNG растеризует UI из SVG листа; несколько файлов упаковывает `zipFiles`.
- Сохранение — `Platform.saveExport`: в десктопе нативный диалог и команда `write_export`, в браузере — скачивание.
- Формат листа и масштаб — настройки документа (`drawing`, команда `setDrawing`), графы основной надписи — сведения о проекте (`setMeta`).

## Команды и горячие клавиши

- Все действия приложения — записи реестра команд (`packages/editor/src/actions`): название, группа, сочетания, доступность. Из реестра строятся палитра ⌘K, шпаргалка клавиш (⌘/) и обработчик клавиатуры.
- Сочетания задаются физическим кодом клавиши (`KeyboardEvent.code`), поэтому работают в любой раскладке. ⌘ на macOS соответствует Ctrl на Windows и Linux.

## Тестирование

- Ядро: юнит-тесты геометрии (стыки, объединение, области, проёмы), команд и истории; сценарии движка (`crates/op-engine/src/tests.rs`) — ввод указателем и клавиатурой как из UI: цепочки стен, числовой ввод, Т-стыки, проёмы, помещения, размеры за узлами, перетаскивание и слияние узлов, удаление, слои, подложка с калибровкой, файл и журнал, комплект листов (состав, масштаб, основная надпись, ведомости, пакет для бригады). Раскладка листов — юнит-тестами (`sheets.rs`), писатели — в `op-export`. Дальше — property-тесты геометрии и снапшот-тесты экспорта (PDF/DXF/XLSX как структура, а не байты).
- Скан: синтетические сканы (`op_scan::synth`) с известным планом — площади комнат, толщина перегородки, проёмы, выравнивание повёрнутого скана, облако PLY без нормалей с определением оси «вверх», ZIP с данными RoomPlan, «пропущенная стена», экран ошибки. Дальше — корпус реальных сканов с метриками точности (стены ±N мм, проёмы, площади).
- Рендерер: кадры на headless wgpu (нативно, бэкенд платформы) с проверкой пикселей: сетка, заливка с отверстием, линии, маркеры, текст, изображение.
- UI: юнит-тесты (`bun test`) и e2e на веб-сборке (Playwright): обмер (`survey.spec.ts`) — стены кликами и с клавиатуры, площадь помещения, проёмы, размер за стеной, удаление и отмена, слои, подложка и калибровка, выноска, файл и журнал; импорт скана (`scan.spec.ts`) — мастер, ответы на вопросы, импорт одним шагом, экран ошибки и обводка, нечитаемый файл; мебель (`furniture.spec.ts`); электрика (`electrical.spec.ts`) — точки у стены, светильники, клавиши выключателя, группы щита и листы; сантехника (`plumbing.spec.ts`) — выводы под приборы, стояки, прокладка, ручная труба, спецификация и листы; отделка (`finish.spec.ts`) — поверхности, плитка с подбором старта, краска и обои, материалы проекта, расход и листы; смета (`estimate.spec.ts`) — типовой прайс, объёмы из модели, ручной объём, группировка по помещениям, закупки, история цен, экспорт XLSX и импорт CSV; импорт DXF стенами (`import.spec.ts`), этажи (`levels.spec.ts`), климат (`climate.spec.ts`), рендер (`render.spec.ts`), гостевая ссылка (`share.spec.ts`).
- Десктоп: на каждый пуш (`ci.yml`) — сборка и самопроверка собранного приложения на macOS, Windows и Linux (запуск окна и движка, бэкенд GPU). Тяжёлые проверки — отдельный workflow `desktop-checks.yml` (вручную и раз в неделю):
  - системные диалоги «Сохранить» и «Открыть», аварийное завершение и восстановление через системный вопрос — на macOS (AppleScript), Windows (SendKeys) и Linux (xdotool), `scripts/desktop-dialogs.sh`;
  - рендер кадра без окна на нативном бэкенде платформы (Metal, D3D12, Vulkan) с проверкой пикселей — `op-render`;
  - WebGPU в настоящем окне Windows (программный адаптер; нестабилен на раннерах без GPU и прогон не валит);
  - e2e настоящего окна на Linux через tauri-driver — файлы и журнал на диске, восстановление после аварийного завершения, стены мышью (события X) и поиск помещений с проверкой файла, импорт скана через нативный диалог. WebDriver для Tauri на macOS не поддерживается.
- WebGPU и WebGL2 в браузере: Playwright, пиксельная проверка сетки, стен, заливки помещения и подписи на обоих бэкендах.
