# Архитектурные решения

Журнал принятых решений. Каждое решение — дата, суть, следствия.

## 2026-11-01 · Распознавание скана — локально, в MVP

Импорт скана Polycam (GLB/ZIP, LiDAR) с автоматическим распознаванием стен, проёмов и комнат входит в MVP. Обработка выполняется на машине пользователя, без сервера.

Следствия:

- Нужен производительный вычислительный модуль для облака точек (~1–2 млн точек): сегментация плоскостей, поиск стен, замыкание контуров, проёмы.
- Мастер импорта: Файл → Обработка → Проверка (сомнительные места с уверенностью) → Параметры. При неудаче: подложка для обводки или пустой проект.

## 2026-11-01 · Импорт из Remplanner — только через их открытый экспорт

Свой парсер закрытого формата `.plan` не пишем (clean room). Перенос проекта возможен через файлы, которые Remplanner выгружает сам (DXF, glTF), и через подложку-изображение.

## 2026-11-01 · Лицензия: AGPL-3.0 + MIT для формата

- Приложение и ядро: AGPL-3.0.
- Схема формата `.oplan` и SDK для работы с ним: MIT.
- Разрешены зависимости под MIT/Apache/BSD/MPL/LGPL/GPL-3.0+. Запрещены GPL-2.0-only (например, LibreDWG).
- TODO: заменить `LICENSE` на AGPL-3.0, вынести схему формата в отдельный пакет с MIT.

## 2026-11-01 · Платформа: Tauri 2 + веб-UI + Rust-ядро

- Оболочка: Tauri 2 (macOS, Windows, Linux).
- Интерфейс: TypeScript, веб-фреймворк (выбор отдельно), холст на WebGL2, WebGPU там, где он доступен.
- Ядро на Rust: модель, геометрия, распознавание скана, экспорт (PDF, DXF, XLSX, IFC). В десктопе работает нативно и многопоточно, для веб-версии собирается в WASM.

Следствия:

- Фронтенд не зависит от Tauri напрямую, а работает через тонкий слой платформы. Если вебвью на Linux (WebKitGTK) станет проблемой, можно перейти на Electron без переписывания фронта и ядра.
- Фотореалистичный рендер позже можно вынести в отдельный нативный процесс.

## 2026-11-01 · Основной стиль UI — плотный

Один плотный интерфейс (в духе Figma и Linear) на все режимы. Отдельный «дружелюбный» режим не делаем. Онбординг строим на пустых состояниях, подсказках в статус-строке и стартовом экране.

## 2026-11-01 · Стадии вместо MVP

Работа идёт стадиями (см. `product-spec.md`). Каждая стадия доводится до рабочего состояния. Урезанного MVP нет.

## 2026-11-01 · Интерфейс: React

Панели, инспекторы, таблицы, диалоги пишем на React + TypeScript. Холст фреймворком не рисуется.

## 2026-11-01 · Модель проекта живёт в Rust-ядре

Ядро — источник истины: документ, команды, отмена/повтор, варианты, производные данные (помещения, площади, трассы, объёмы сметы). Фронтенд отправляет команды и получает диффы. Временную графику во время перетаскивания рисует рендерер, без коммита в модель.

## 2026-11-01 · Один рендерер на wgpu (2D и 3D)

- 2D-план, облако точек скана и 3D-вид рисует один рендерер на Rust + wgpu.
- Рендерер собирается в WASM и рисует в `<canvas>` вебвью. Бэкенд — WebGPU там, где он есть, иначе WebGL2.
- Линии постоянной толщины, штрихи и штриховки — в шейдерах. Тесселяция — lyon. Текст — MSDF.
- Ограничение: в режиме WebGL2 нет compute-шейдеров. Всё, что от них зависит, должно иметь CPU-путь.
- Тяжёлый оффлайн-рендер (очередь фотореалистичных кадров) позже можно вынести в нативный wgpu-процесс без окна.

## 2026-11-01 · Файл проекта `.oplan` — ZIP-контейнер

- Внутри: манифест с версией формата, модель (JSON), бинарные данные скана, превью, рендеры, ресурсы.
- Модель читаемая и диффится. Схема публикуется под MIT.
- Автосохранение пишет журнал изменений рядом с файлом и периодически пересобирает контейнер.

## 2026-11-01 · Основная ОС — macOS

Разработка и ручное тестирование — в первую очередь на macOS (WKWebView). Windows и Linux собираются и проходят тесты в CI.

## 2026-11-01 · Ядро и рендерер — один WASM-модуль в Web Worker

```
Вебвью
 ├─ UI-поток: React
 │     ↕ postMessage (команды → ядро; диффы и выборки → панели)
 └─ Web Worker: WASM [ядро модели + wgpu-рендерер] → OffscreenCanvas
Tauri (нативный Rust)
 └─ сервисы: файловая система, .oplan, распознавание скана, экспорт PDF/XLSX/DXF/IFC
```

- Геометрия попадает из модели на GPU без сериализации. UI-поток не блокируется.
- Ядро и сервисы — одни и те же crates. Они компилируются в WASM (воркер, веб-версия) и нативно (Tauri, CLI, тесты).
- В веб-версии нативные сервисы заменяются WASM-реализациями или File System Access API.

## 2026-11-01 · Вход скана: LiDAR-сетка/облако + Room-данные

- Если экспорт содержит параметрические стены и проёмы (Room-режим, Apple RoomPlan), используем их как сильную подсказку.
- Основной путь — свой геометрический конвейер по LiDAR-сетке или облаку точек: пол и потолок → вертикальные плоскости → линии стен на плане → проёмы → замкнутые контуры комнат. Каждый вывод получает оценку уверенности.
- Скан сохраняется в `.oplan` и служит подложкой в 2D и 3D.

## 2026-11-01 · Стили: CSS Modules + дизайн-токены

- Компоненты стилизуются через CSS Modules.
- Токены (цвета, отступы, радиусы, тени, типографика) — CSS-переменные, светлая и тёмная темы.
- Без CSS-in-JS в рантайме.

## 2026-11-01 · Язык: русский + каркас i18n

- Все строки UI проходят через каталог сообщений с первого дня. Пока есть только русская локаль.
- Нормативы (СПДС в штампе, нормы освещённости, высоты монтажа, правила ПУЭ, уклоны) вынесены в подключаемый «профиль страны». Первый профиль — РФ.
- Форматирование чисел, единиц и дат — по локали (десятичная запятая, неразрывные пробелы в разрядах).

## 2026-11-01 · Монорепо: Cargo workspace + Bun + Vite

- Rust: Cargo workspace в `crates/`.
- TS: Bun workspaces (менеджер пакетов и запуск скриптов), Vite для дев-сервера и сборки фронта.
- Раскладка: `apps/` (desktop, web), `packages/` (ui, editor, engine-client), `crates/` (op-model, op-geom, op-render, op-engine, op-format, op-scan, op-export, op-calc), `schema/`. `op-format` и `schema/` — под MIT.

## 2026-11-01 · Состояние UI: Zustand

Проекции модели (выделение, свойства, списки), состояние панелей и настроек хранятся в Zustand-сторах. Диффы из воркера применяются в одном месте, компоненты подписываются селекторами.

## 2026-11-01 · Протокол UI ↔ воркер: JS-объекты + типы из Rust

- Сообщения — обычные JS-объекты (serde-wasm-bindgen) через `postMessage`.
- Большие буферы — `Transferable`.
- TS-типы сообщений и сущностей генерируются из Rust-типов. Рукописных дублей нет.

## 2026-11-01 · UI-примитивы: Base UI

Неоформленные примитивы (меню, поповеры, диалоги, тултипы, NumberField и т.п.) — Base UI. Стили наши, на CSS Modules.

## 2026-11-01 · TS-типы из Rust: tsify

Типы сообщений воркера и сущностей модели генерируются через tsify и попадают в `.d.ts` WASM-модуля. Для команд Tauri — тонкий типизированный слой на тех же типах.

## 2026-11-01 · PDF: krilla

Векторные листы, шрифты с сабсеттингом, PDF/A. Штамп СПДС, таблицы и раскладку листа верстаем сами. Поддержку слоёв PDF (OCG) нужно проверить на ранней стадии, при необходимости — доработать.

## 2026-11-01 · IFC 4: собственный писатель STEP

Пишем нужное подмножество IFC 4 (стены, проёмы, помещения, мебель, этажи) на Rust без внешних зависимостей. В CI проверяем результат через IfcOpenShell (только в тестах, в дистрибутив не входит).

## 2026-11-01 · Rust: rustfmt + строгий clippy

- `rustfmt` с общим `rustfmt.toml`.
- clippy в CI с `-D warnings`, плюс выборочные pedantic-правила в `[workspace.lints]`. Среди них: запрет `unwrap`/`expect` в библиотечном коде, контроль приведений чисел (`cast_possible_truncation`, `cast_sign_loss` и т.п.), `float_cmp`.

## 2026-11-01 · Проверки: Lefthook + CI

- Lefthook перед коммитом: формат и быстрый линт только изменённых файлов, проверка сообщения коммита.
- CI: полный формат-чек, clippy, линт TS, `tsc --noEmit`, тесты Rust и TS, сборка под macOS, Windows, Linux.

## 2026-11-01 · Коммиты: Conventional Commits

`feat(scan): …`, `fix(model): …`, `docs: …` и т.д. Скоупы соответствуют crates и пакетам. Changelog и версия собираются из истории.

## 2026-11-01 · TS/CSS/JSON: Biome

- Biome — линтер и форматтер для TS, TSX, CSS (включая CSS Modules) и JSON, один конфиг `biome.json` в корне.
- Типы проверяет `tsc --noEmit` в CI.
- `bun lint` / `bun fmt` рассмотрены. Вернёмся к ним, когда линтер появится в стабильном Bun.

## 2026-11-01 · Файлы, журнал и автосохранение (стадия 0)

- Байты `.oplan` собирает и разбирает движок (op-format в WASM). Нативная часть только читает и пишет файлы. Поэтому десктоп и браузер работают одинаково.
- Журнал автосохранения — JSON Lines операций истории (`execute`/`undo`/`redo`) с заголовком версии формата. Оборванная последняя строка отбрасывается.
- Проект с файлом автосохраняется раз в 30 секунд. Несохранённый проект живёт в журнале восстановления и предлагается к восстановлению при следующем запуске.
- Перед открытием другого проекта изменения проекта с файлом сохраняются молча, для проекта без файла — спрашивается подтверждение.

## 2026-11-01 · Палитра команд — своя, без cmdk

Палитра построена на Base UI Dialog и общем реестре команд. Отдельная библиотека не нужна: поиск по словам и навигация с клавиатуры занимают несколько десятков строк, а реестр всё равно нужен для горячих клавиш и шпаргалки.

## 2026-11-01 · Тесты TS: bun test + Playwright

Юнит-тесты фронтенда — `bun test`. E2E — Playwright по веб-сборке в Chromium (WebGL2 через SwiftShader в CI).

## 2026-11-02 · Linux: включаем WebGL в воркерах WebKitGTK

WebKitGTK по умолчанию не даёт WebGL2 в `OffscreenCanvas` внутри Web Worker (флаг `AllowWebGLInWorkers` стабилен, но выключен), и движок на Linux не запускался. Нативная часть при старте включает этот флаг через API WebKitGTK 2.42+ и перезагружает страницу (`apps/desktop/src-tauri/src/linux.rs`). Найдено при запуске настоящего окна под Xvfb; сборка в CI этого не ловила.

## 2026-11-02 · Проверка десктопа в CI

- Самопроверка на macOS, Windows и Linux: собранное приложение запускается с `OPENPLANNER_SELFTEST=<файл>`, ждёт старта движка и записывает бэкенд GPU (`scripts/desktop-selftest.sh`).
- На Linux дополнительно — e2e настоящего окна (Xvfb + openbox, tauri-driver/WebKitWebDriver, xdotool): нативные диалоги сохранения и открытия, файлы и журнал на диске, восстановление после `kill -9` (`scripts/desktop-e2e.sh`). На macOS WebDriver для Tauri недоступен, поэтому там только самопроверка.

## 2026-11-02 · WebGPU: фактическое состояние

Самопроверка в CI показывает, что движок запускается на всех трёх ОС, и сообщает, почему выбран бэкенд:

- macOS (WKWebView) и Windows (WebView2): `navigator.gpu` в воркере есть, но виртуальные машины CI не выдают адаптер — движок работает на WebGL2.
- Linux (WebKitGTK): `navigator.gpu` нет — только WebGL2.

Определение WebGPU работает: на машине с GPU, который браузер выдаёт, будет выбран WebGPU. Проверить это можно только на реальном железе — подсказка у статуса «GPU:» в статус-строке показывает диагностику.

## 2026-11-02 · Проверка WebGPU и системных диалогов

- WebGPU-путь движка проверяется в e2e (Playwright, проект `webgpu`): Chromium с программным адаптером SwiftShader, бэкенд обязан быть `BrowserWebGpu`, а на холсте должна быть видна сетка. Тот же пиксельный тест — для WebGL2.
- Windows: настоящее окно (WebView2) запускается с флагами `--enable-unsafe-webgpu --ignore-gpu-blocklist` (программный адаптер D3D12 WARP на раннере без GPU), самопроверка обязана получить `BrowserWebGpu`. Флаги передаются через `additional_browser_args` при создании окна (`OPENPLANNER_WEBVIEW2_ARGS`): переменную `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` WebView2 под Tauri не применяет. Поэтому главное окно создаётся в коде (`create: false` в `tauri.conf.json`).
- Системные диалоги «Сохранить» и «Открыть» проверяются на macOS (AppleScript), Windows (SendKeys) и Linux (xdotool): приложение в сценарии `dialogs` само вызывает команды, драйвер `scripts/desktop-dialogs.sh` проходит диалоги с клавиатуры, итог сверяется с файлом на диске.
- CI на macOS — `macos-26` (основная ОС проекта). На виртуальной машине раннера WKWebView не выдаёт WebGPU-адаптер, а программного адаптера у WebKit нет, поэтому окно на macOS в CI работает на WebGL2. Рендерер на Metal проверяется нативным тестом: `op-render` рисует кадр сетки через wgpu на Metal-GPU раннера (WGSL → MSL), кадр читается и сверяется по пикселям. Тот же тест идёт на D3D12 (Windows) и Vulkan (Linux, lavapipe).
- Восстановление после сбоя на всех ОС: сценарии самопроверки `crash` (открыть файл, правка, запись журнала, затем `kill -9`) и `recover` (открыть файл, системный вопрос о восстановлении, сверка правки).

## 2026-11-02 · WebGPU в окне по платформам: что возможно

- Windows (WebView2): WebGPU работает, проверено в CI в настоящем окне (`BrowserWebGpu`).
- Linux (WebKitGTK 2.52 из Ubuntu): WebGPU в сборке отсутствует — `navigator.gpu` нет даже с включённой возможностью `WebGPU` в настройках WebKit (проверено в настоящем окне). Движок работает на WebGL2, как и задумано решением о бэкендах.
- macOS (WKWebView): `navigator.gpu` есть, но на виртуальной машине CI (`Apple Paravirtual device`) адаптер не выдаётся, программного адаптера у WebKit нет. Тот же рендерер на Metal этой машины проходит нативный тест кадра. WebGPU в окне на macOS проявится на реальном Mac с GPU; подсказка у «GPU:» в статус-строке показывает бэкенд и причину выбора.

## 2026-11-02 · Стадия 0 закрыта

Стадия 0 принята. Проверено в CI на настоящем приложении (macOS 26, Windows, Linux): запуск окна и движка, системные диалоги сохранения и открытия, восстановление после аварийного завершения, рендер кадра на Metal / D3D12 / Vulkan; WebGPU в окне — на Windows. ## 2026-11-02 · Помещения: точка подписи + вычисляемый контур

Помещение хранит точку подписи и свои свойства (название, высота потолка). Контур, площадь и периметр движок вычисляет: это замкнутая область стен, в которой лежит точка. Правка стен (сдвиг узла, разрезание, Т-стык) помещение не ломает. Команда «Найти помещения» создаёт помещения во всех замкнутых областях без помещения.

Области ищутся без топологии графа: контуры стен объединяются (булевы операции, `i_overlay`), отверстия объединения — области пола, фигуры внутри отверстия — острова (колонны, отдельные стены). Площадь — по поверхностям стен, за вычетом островов. Проёмы помещение не размыкают.

## 2026-11-02 · Стены: граф узлов, толщина по сторонам, стыки

Стена соединяет два узла; толщина задаётся вместе с линией привязки (по оси, слева, справа — по направлению рисования) и раскладывается на толщину по каждую сторону от линии узлов. В узле соседние по углу стороны продлеваются до пересечения (усовое соединение), слишком острый угол срезается. Т-стык не требует разрезать основную стену: конец примыкающей стены лежит на её оси, и объединение контуров даёт чистый стык. Пересекающиеся стены тоже не разрезаются.

## 2026-11-02 · Текст на холсте: SDF-атлас в рендерере

Текст (размеры, подписи помещений, выноски, длина рисуемой стены) рисует тот же wgpu-рендерер. Шрифт Onest Medium (SIL OFL 1.1) встроен в движок; глифы кириллицы, латиницы и символов растеризуются при первом обращении, по растру строится поле расстояний (обычный SDF, не MSDF: на размерах подписей плана разницы почти нет, кода заметно меньше). Мелкий текст усредняется по четырём точкам пикселя, светлая обводка рисуется отдельным проходом под всеми буквами. Размер текста задаётся в мм плана (масштабируется с планом, 2,6 мм на листе 1:50) или в пикселях экрана (подсказки инструментов).

## 2026-11-02 · Слои: системные и пользовательские

В новом проекте есть системные слои «Подложка», «Помещения», «Стены», «Проёмы», «Размеры», «Выноски»; новый элемент попадает в слой своего типа. Элемент можно перенести в другой слой в инспекторе, пользователь может добавлять свои слои. Скрытый слой не рисуется и не участвует в привязках и выделении; заблокированный рисуется, но не выделяется и не правится на холсте. Видимость и блокировка — часть документа (сохраняются в файле, отменяются). Помещения вычисляются по всем стенам, в том числе скрытым.

## 2026-11-02 · Размеры привязаны к узлам

Конец размера, поставленный на узел стены, ссылается на узел и следует за ним; поставленный в пустое место — хранит координаты. При удалении узла размер становится свободным в его последнем положении.

## 2026-11-02 · Правки — обобщённые команды над элементами

Кроме команд над свойствами проекта, документ меняется четырьмя видами команд: `put` (вставить или заменить элемент), `remove` (удалить; на элемент не должны ссылаться), `putAsset`/`removeAsset` (двоичные файлы проекта) и `batch` (несколько команд как одно действие: применяются все или ни одной). Инструменты движка собирают из них правки (стена с новыми узлами, удаление с зависимыми, слияние узлов), каждая правка — один шаг отмены и одна строка журнала. Идентификаторы элементов — монотонные ULID, их выдаёт движок, поэтому воспроизведение журнала детерминировано.

## 2026-11-02 · Подложка: файл в `.oplan`, расшифровка в движке

Изображение подложки (PNG, JPEG) хранится в `.oplan` как есть, в папке `assets/` (без повторного сжатия), а в журнале — в base64 внутри команды `putAsset` (восстановление после сбоя возвращает и картинку). Расшифровывает изображение движок (крейт `image` с PNG и JPEG) — одинаково в WASM и нативно, проверяется обычными тестами. Слишком большое изображение уменьшается до лимита текстуры GPU. Калибровка: два щелчка по подложке и настоящая длина отрезка с клавиатуры; масштаб подложки меняется относительно первой точки.

## 2026-11-02 · Формат 2

Формат `.oplan` версии 2: слои, узлы, стены, проёмы, помещения, размеры, выноски, подложки, папка `assets/`. Миграция 1 → 2 добавляет системные слои и пустые списки. Тег вида элемента в JSON — `type` (поле `kind` занято типом проёма).

## 2026-11-02 · Скан: форматы и конвейер распознавания

- Входные форматы: GLB (glTF 2.0 Binary, экспорт Polycam по умолчанию), OBJ, PLY (облако точек или сетка, ASCII и двоичный), ZIP с любым из них и параметрическая комната Apple RoomPlan (`CapturedRoom`, JSON). Разбор — свой, без зависимостей (`crates/op-scan/src/io`). Сжатие Draco и внешние буферы glTF не поддерживаются — сообщение об ошибке.
- Если есть данные RoomPlan, стены и проёмы берутся из них (уверенность из файла); сетка из того же архива — для вида сверху.
- Свой конвейер по сетке или облаку: выборка поверхности с нормалями и площадью → пол и потолок по гистограмме высот горизонтальных поверхностей → ориентации стен по нормалям в полосе выше мебели → грани стен по гистограмме смещений → сетка заполненности грани (50 × 100 мм) → участки, проёмы (пустоты с перемычкой; пустота за мебелью отбрасывается) → пары граней дают стену с измеренной толщиной, одиночная грань — стену телом наружу (толщина — параметр) → стыки и Т-стыки сводятся, соосные участки склеиваются.
- План выравнивается по главному направлению стен и сдвигается к началу координат.
- Вопросы проверки: «лишняя стена?» (не доходит до потолка — мебель; короткая; слабая опора), «пропущена стена» (свободные концы до 4 м вдоль одной из ориентаций), «дверь или арка?» (по ширине и высоте проёма). Уверенность в процентах; от 50 % предложение принято по умолчанию.
- Неудача распознавания (нет пола, меньше трёх стен) — не ошибка: мастер показывает экран с вариантами «Пересканировать», «Обвести по скану» (только вид сверху подложкой и инструмент «Стена»), «Начать с пустого проекта».

## 2026-11-02 · Скан обрабатывается в отдельном воркере WASM

Распознавание выполняется тем же WASM-модулем движка во втором Web Worker — одинаково в десктопе и в браузере, с прогрессом по этапам и отменой (воркер останавливается). Редактор при этом не замирает. Нативный многопоточный путь (rayon в Tauri), заложенный в архитектуре, отложен: на квартирном скане обработка занимает секунды. Вернёмся к нему, если реальные сканы окажутся медленными.

## 2026-11-02 · Скан в проекте: слой «Скан» и папка `scan/`

- Вид сверху (пол светлым, стены тёмным) — PNG-подложка на системном слое «Скан» в самом низу; слой можно скрыть или заблокировать.
- Исходный файл скана сохраняется в `.oplan` в папке `scan/` (параметр мастера, по умолчанию включён) — понадобится для 3D (стадия 5). В журнал автосохранения он попадает в base64; в браузере журнал хранится в localStorage с лимитом в несколько мегабайт, поэтому большие сканы в веб-версии лучше сохранять в файл сразу.
- Импорт — одна правка: высота потолка, узлы, стены, проёмы, помещения, подложка и исходный файл; одна отмена убирает всё.
- Формат 3: системный слой «Скан», файлы `scan/`. Миграция 2 → 3 добавляет слой.

## 2026-11-02 · Тестовые сканы — синтетические

Реальных сканов Polycam в репозитории нет (clean room: чужие файлы не берём). Тесты используют генератор `op_scan::synth`: поверхности комнат такими, какими их видит LiDAR изнутри (только внутренние стороны стен), с проёмами, шкафом у стены, закрывающим стену, шумом и поворотом плана. Фикстура e2e `apps/desktop/e2e/fixtures/apartment.glb` создаётся примером `cargo run -p op-scan --example synthetic_scan`. Точность на реальных сканах проверяется по мере появления своих сканов; метрики корпуса — отдельная задача.

## 2026-11-02 · Варианты — поле `variant` у элементов и список демонтажа

- Обмер — элементы без поля `variant`; он общий для всех вариантов, поэтому правка обмера сразу видна в каждом варианте.
- Новые элементы варианта — те же элементы (узлы, стены, проёмы, помещения, размеры, выноски) с `variant: <id>`. Ссылаться они могут на обмер или на свой вариант, но не на чужой — проверка в `op-model`.
- Вариант (`Variant`) хранит название и список демонтированных элементов обмера (`demolished`): стены, проёмы, помещения. Проёмы демонтированной стены уходят вместе с ней и отдельно не перечисляются.
- Вид варианта — проекция документа (`op_model::view::project`): обмер без демонтажа плюс элементы варианта. Инструменты, привязки и площади работают с проекцией, поэтому весь код стадии 1 работает в варианте без изменений.
- Статус элемента вычисляется, а не хранится: «существующий» — элемент обмера, «демонтаж» — элемент обмера из списка варианта, «новый» — элемент варианта.
- Почему не копии плана на каждый вариант: правка обмера должна попадать во все варианты (требование стадии 3), а копии пришлось бы синхронизировать. Почему не дифф-патчи над обмером: удаление и правка элементов обмера в варианте не нужны (их демонтируют и строят новые), а простой список демонтажа легко проверять и показывать.

## 2026-11-02 · Правки в варианте адаптирует движок

Инструменты строят команды как раньше; перед выполнением движок адаптирует их к виду (`crates/op-engine/src/variants.rs`):

- в варианте новые элементы получают `variant`, новые стены — материал инструмента; правка элемента обмера отбрасывается (обмер правят в режиме «Обмер»); удаление стены, проёма или помещения обмера превращается в демонтаж;
- в обмере удаление узла или стены уносит зависящие от них элементы вариантов (стены на удалённых узлах, их проёмы и размеры) и чистит списки демонтажа — одной правкой, одна отмена всё возвращает.

Отдельный инструмент «Демонтаж» (X) переключает статус щелчком; в инспекторе тот же выбор — «Существующий / Демонтаж». Демонтированные элементы рисуются красной штриховой обводкой поверх плана варианта и остаются выбираемыми.

## 2026-11-02 · Материал перегородок и сравнение вариантов

- Материал — у стены (`Wall.material`: газобетон, ГКЛ, кирпич), выбирается для инструмента «Стена» в варианте; толщина по умолчанию 100 / 100 / 120 мм. Новые стены заливаются цветом материала.
- Сводка (`VariantsSummary`) считается движком после каждой правки для обмера и всех вариантов: помещения с площадями, общая площадь, демонтаж стен (м и м² по высоте потолка), новые стены по материалам, новые и заложенные проёмы. Метки помещений обмера, оказавшиеся в одной области (снесли перегородку), считаются одним помещением — площадь не задваивается.
- Синхронный просмотр — вид `compare`: две проекции рядом на одном холсте с подписями; только просмотр, инструменты недоступны, Esc — выход. При выходе камера возвращается туда, где была до сравнения.
- Формат 4: список `variants`, поля `variant` и `material`. Миграция 3 → 4 добавляет пустой список вариантов.

## 2026-11-02 · Экспорт чертежей: свои писатели в `op-export`, работают в движке

- Лист — векторное описание в миллиметрах бумаги (`op_export::Sheet`): заливки, линии, текст по слоям и видовые экраны с планом в масштабе. Из одного описания пишутся PDF, SVG и DXF; таблицы листа — ещё и в XLSX.
- Писатели свои, без внешних библиотек форматов (зависимости — `flate2`, `zip`, `ab_glyph`, `base64`):
  - PDF: слои — группы необязательного содержимого (OCG), шрифт Onest встроен как CIDFontType2 / Identity-H с ToUnicode, поэтому кириллица ищется и копируется;
  - DXF R12: план из видовых экранов в натуральную величину по слоям, строки в cp1251;
  - XLSX: несколько таблиц на листе книги, числовые форматы.
- Пересматривает решение «PDF: krilla» (2026-11-01): слои OCG проверены в своём писателе, модуль WASM не растёт на библиотеку PDF. **Ждёт подтверждения владельца.**
- Листы собирает движок (`crates/op-engine/src/sheets.rs`) в воркере, а не нативная часть: экспорт одинаков в десктопе и браузере. Нативная часть только записывает байты: команда `write_export` принимает пути с расширениями `pdf`, `svg`, `dxf`, `png`, `xlsx`, `zip`.
- PNG растеризует UI из SVG листа, где текст записан контурами (150 dpi); несколько листов движок упаковывает в ZIP (`zipFiles`).

## 2026-11-02 · Комплект листов стадии 4

- Состав: обмерный план всегда; для варианта — план демонтажа (если что-то демонтируется или прорезается), план монтажа перегородок (если есть новые стены или закладка проёмов) и план помещений после перепланировки. Тематические листы мебели, инженерии и отделки появятся вместе со своими стадиями.
- Все листы комплекта — в одном масштабе и с одним положением плана: их можно накладывать. Масштаб подбирается по самому тесному листу из ряда ГОСТ 2.302 и не крупнее 1:50 (основной масштаб планов квартир); заданный вручную масштаб сохраняется в проекте (`drawing.scale`), если план не помещается — предупреждение.
- Раскладка: таблицы и легенда справа от плана столбцом над основной надписью или под планом — выбирается вариант, где план крупнее и меньше таблиц уходит на продолжение. Длинная таблица делится по строкам, остаток — на листы «(продолжение)».
- Основная надпись — в габаритах формы 3 ГОСТ Р 21.101; графы — из сведений о проекте (`meta`: шифр, стадия, организация, разработал, проверил), дата (ММ.ГГ) приходит из UI.
- Демонтируемое — красная штриховка со штриховым контуром, возводимое — заливка и штриховка материала, закладка проёмов — своя штриховка. Марки на плане (Д1…, П1…) ссылаются на строки ведомостей; экспликация нумерует помещения.
- Скрытые слои и подложки на листы не попадают.
- Форматы: PDF — все листы в одном файле; SVG и DXF — по листу, несколько листов — ZIP; XLSX — экспликации и ведомости (смета — стадия 10). «Пакет для бригады» — PDF чертежей и XLSX ведомостей одним ZIP.
- Формат 5: `meta` получает графы основной надписи, документ — настройки чертежей (`drawing`: формат листа и масштаб).

## 2026-11-02 · Развёртки стен

- Лист «Развёртки стен» замыкает комплект и строится по итоговому виду: вариант, если он выбран, иначе обмер. Помещения — в порядке экспликации, только с замкнутым контуром.
- Грани — стороны контура помещения по часовой стрелке от верхнего левого угла; каждая показана изнутри помещения (левый край грани — слева). Грани короче 100 мм (торцы, стыки) не разворачиваются. Буквы стен — как для осей по ГОСТ 21.101, без похожих на цифры (З, О, Ч и т. п.); рядом — схема помещения с буквами.
- Проём попадает на грань, если лежит в стене, грань которой совпадает с гранью помещения; дверь видна из обоих помещений. На развёртке — контур проёма, у двери — треугольник от петель к ручке, у окна — рама и импост; размеры: цепочка по краям проёмов, общий размер, высота помещения, низ и верх проёмов.
- Масштаб развёрток — 1:50 или мельче, если самая длинная стена не помещается; от масштаба планов не зависит. В DXF развёртки лежат в модели в натуральную величину, без пересечений.
- «Площади стен»: периметр по граням, площадь стен на высоту потолка, проёмы в пределах высоты, чистая площадь — основа для отделки (стадия 9). Таблица идёт на лист и в XLSX («Стены»).
- Мебель, розетки и отделка на развёртках появятся со своими стадиями.
